## WATCH — Google Antigravity SDK local-model support

### What changed

On 23 September 2026 Google announced local, fully offline agent workflows in the Antigravity Python SDK, initially optimized for Gemma 4 26B A4B through LiteRT-LM. The SDK also accepts OpenAI-compatible local servers such as Ollama, LM Studio and vLLM while retaining its orchestration layer.

Primary sources:

- https://developers.googleblog.com/introducing-support-for-local-ai-models-in-the-antigravity-sdk/
- https://github.com/google-antigravity/antigravity-sdk-python

### Why it matters for WijSAmen

This is a credible future route for Autonoompje's model-independent local/cloud split: private files can remain local, the orchestration layer can stay stable while backends change, and explicit hooks/policies can separate read-only work from writes. That aligns with the Continuity Layer, Action Authorization Compiler and the planned local AI PC.

### Maturity and access

- Public Python package and Apache-2.0 repository: technically available.
- Google's preferred local path currently uses Gemma 4 26B A4B and recommends at least 24 GB VRAM or shared memory plus a 64K context.
- This is not a practical Samsung Galaxy A52s/Termux target and current suitable PC hardware is not verified.
- Google's demonstration results are vendor evidence, not independent reliability or quality validation.

### Smallest reversible test

Do not buy or install anything yet. Once a machine with at least 24 GB suitable memory is already available, run one isolated read-only smoke test:

1. pin package and model versions in a disposable virtual environment;
2. expose only a temporary directory containing three synthetic project files;
3. deny writes and network access;
4. ask the agent to produce a source-linked continuity summary;
5. compare completeness, hallucinations, latency, peak memory and recovery after interruption with the current Autonoompje baseline.

Success: all source claims resolve to the three files, no denied action occurs, restart recovery works and resource use fits the machine. Failure: unsupported claims, policy bypass, state loss or unusable latency. Rollback: delete the environment, model copy and temporary directory.
